# Share images use their own font file and fontconfig settings

A Post without a cover gets a share image generated at build time with `sharp`'s text input, so it adds no dependency (ADR 0002) and Satori isn't needed. `sharp`'s libvips draws text with Pango, and its bundled fontconfig reads the build machine's `/etc/fonts`. A spike showed that this changes the pixels: the same title rendered differently with Fedora's configuration, with no configuration (as on a bare Ubuntu image) and with full hinting or no antialiasing. So the renderer, `src/share-image/render.ts`, points `FONTCONFIG_FILE` at the Theme's own `src/share-image/fonts.conf` before it draws any text. That configuration lists no font folders and fixes antialiasing, hinting and subpixel settings, so the only font is the one passed as `fontfile` and nothing about the machine's fonts changes the result. The font file is a committed copy of Schibsted Grotesk's variable TTF from Google Fonts (OFL, with its license alongside), not the copy the Fonts API downloads, which is WOFF2 in Astro's cache: a committed file builds offline and can't change under a published site. With this, one build's share images were byte-identical across repeated builds, a clean install, Fedora and an Ubuntu 24.04 container, and the spike's render was unchanged with SIMD turned off in libvips and pixman. The costs: swapping the site's typeface doesn't swap the share image's, which the README says, and a title with characters outside Schibsted Grotesk falls back to no other font. No stored hash of the image is tested, so a change in a future `sharp` release shows up as a different image rather than a failing test.

The share images also show the site's favicon, `public/favicon.svg`, as a logo. `sharp` rasterizes it with librsvg, a different path from the text, so it was checked the same way: with the logo, one build's share images were byte-identical across repeated clean builds and between Fedora and an Ubuntu 24.04 container. The favicon draws no text, so fontconfig plays no part in it.

GitHub's runners then built the release (commit ff3338d) in four parallel `ubuntu-latest` jobs, which landed on AMD EPYC 9V74 CPUs with AVX-512 and an AMD EPYC 7763 without it. All 11 share images were byte-identical in every job to the local build on an Intel CPU without AVX-512, so the CPU-specific code paths in libvips, pixman and the PNG encoder don't change the result either.
